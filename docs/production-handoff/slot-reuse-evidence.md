The finalization transaction requires the independent fence observation to follow the durable start of the current reconciliation epoch. The stored clock is a lower bound. A qualified adapter must wait for `BeginReconciliation` to return its committed barrier before collecting the new bounded inventory and observing the continuing fence. Historical settlement can predate reconciliation. Teardown must follow the last positive physical inventory observation of the candidate. Re-labeling a pre-barrier fence with the current epoch cannot fund release. The regression fixture proves refusal with the full charge and no tombstone, followed by release once with a fresh fence observation. It exercises the local transition with an offline source and provides no installed-stack qualification.

## Reconciliation identity and release history

The gateway can identify physical rows in the existing authenticated Incus v6.0.4 recursive inventory response. It collects the controller, pool, reservation tag, actual CPU and RAM bounds, creation time, instance UUID and generation. It binds those fields to the daemon key and project scope pinned before collection. Missing identity fields, a conflicting returned project or a creation time in the future leave the allocation opaque. These project-scoped facts establish neither job settlement nor storage reclamation. Stock gateway inventory uses instance names and has no qualified producer of original source/route-bound retirement receipts.

SQLite schema 31 records the original physical identity alongside the charged inventory row on first import. Each complete reconciliation can confirm that identity for its own epoch. Missing rows, opaque observations and previously unidentified rows cannot establish independence. A changed physical subject permanently excludes that row from slot-reuse evidence. If authenticated observations establish different UUID-generation pairs or different creation times under the same accounting key, the ledger records the conflict and keeps admission closed across new inventories and restart. The existing allocation row cannot represent both possible charges. No automatic identity-resolution procedure exists. Inventory allocations continue to include these rows. The gateway binds the post-barrier list request to the random nonce returned by that reconciliation. The transport seals its digest into the observation. The writer requires a matching nonce, a collection start after the barrier, and the original durable host enrollment. Replaying an earlier response after a clock rollback still fails.

Finalization with a qualified fixture source requires a deleting reservation and its exact deleting inventory row, original route-scoped ID and full CPU, RAM, disk and runner charge. The independent teardown must follow the last positive instance observation. Every other inventory row must carry current evidence of a distinct incarnation. A matching UUID and generation anywhere across hosts or routes, a duplicate scoped resource ID, or an ambiguous row retains the charge. With two independently identified runners, the transaction can release the exact settled runner and preserve the second runner's entire allocation.

The same writer transaction records an immutable retirement index alongside the release tombstone. Indexed lookups cover the physical UUID and generation across enrollment changes, the scoped ID, and unidentified history. This avoids reading historical evidence blobs or walking the reservation history on each finalization. An exact request replay returns the original decision and grants zero additional credit, including after restart.

## Upgrade and rollback

Upgrading invalidates readiness and any in-progress fence. Existing inventory and release records retain their charges and replay semantics. Schema 31 marks all pre-upgrade inventory identities and release tombstones opaque. A later observation under the same name cannot establish the original identity of a legacy inventory row. The presence of even one unindexed legacy release blocks all new slot-reuse credits in that ledger. This conservative migration avoids deriving an original incarnation from incomplete historical records. The one-time work to build the new indexes scales with ledger size.

Schema 30 handles refuse writes against the newer format, and the old binary refuses to open the migrated store. Keep the migrated ledger and disable further releases to stop the feature. A pre-upgrade consistent backup is historical and cannot authorize current admission or replay previously spent capacity. The stock release registry remains empty.

The [slot-reuse handoff](https://github.com/ShortCipher5/garm-capacity-controller/pull/392) defines the installed-stack acceptance criteria.
