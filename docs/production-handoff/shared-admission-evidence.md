# Shared admission for ordinary stock GARM pools

**Production enforcement remains unqualified.** On unmodified GARM v0.2.1, each ordinary repository pool selects its own external provider. A provider can refuse a create before it starts backend work. Selecting that provider for one pool gives no coverage over a different provider serving another pool. The controller's shared-capacity planner has no runtime grant or settings authority. [Production plan #394](https://github.com/ShortCipher5/garm-capacity-controller/pull/394) · [Offline planner #398](https://github.com/ShortCipher5/garm-capacity-controller/pull/398)

The ordinary repository, organization and enterprise managers all use the same base pool manager. At the pinned revision the only calls from GARM into a provider's native `CreateInstance` interface are the ordinary pending worker and the scale-set worker. A provider boundary can cover native CPU, RAM, runner count and applicable disk only for calls routed to that authority. Stock can obtain JIT registration before the provider call. A refusal therefore prevents native provision on that route while GARM still owns any pending row, registration and cleanup. [Ordinary pool manager factories](https://github.com/cloudbase/garm/tree/154638445c3949c1958b01812f69d9a1e4d82684/runner/pool) · [Ordinary provider call](https://github.com/cloudbase/garm/blob/154638445c3949c1958b01812f69d9a1e4d82684/runner/pool/pool.go#L1124-L1148) · [Scale-set provider call](https://github.com/cloudbase/garm/blob/154638445c3949c1958b01812f69d9a1e4d82684/workers/provider/instance_manager.go#L229-L251)

The proposed managed path covers enrolled ordinary repository pools on one dedicated route. Stock organization and enterprise pools, scale sets, other named provider routes and any independent native writers are outside that enrollment. Each must be proven physically isolated from the managed capacity domain or reach the same durable budget with a qualified ownership and recovery contract. A read filtered by provider or repository cannot prove that isolation. Keep the shared domain inactive until the required installed inventory and write boundaries are independently verified.

## Two independent disposable fixtures

1. **Stock provider selection.** The pristine GARM pool-manager fixture creates two ordinary pools with different named providers and positive maxima. Each accepts a row with fixture JIT data. The fixture lowers each saved maximum to zero before the actual pending worker runs. The worker calls each pool's selected provider once. The refusing provider gets a cleanup request and its row ends in error. The other provider reports success and its own row ends in running. Both providers are mocks. This demonstrates the limit of a per-provider hook and a pool-setting change without creating any instance. The pinned compatibility workflow runs this case on the unpatched source tree. [Fixture](../../integration/garm-v0.2.1/shared-admission-pool-test.go.txt) · [Pinned harness](../../integration/garm-v0.2.1/management-test.sh)
2. **Shared ledger boundary.** A consumed stock grant already charges one host. Two independent SQLite handles then race a stock grant for a second pool against an ordinary placement for the remaining host. Exactly one commits. Closing both handles and reopening preserves the exact total CPU, RAM and runners, the two host subtotals, and the winning pool's charge. Replaying the original stock placement returns its original request, and a fresh placement remains denied. This exercises the canonical accounting boundary for cooperating callers only. ## What the enrolled ledger now enforces

Once a repository policy has been saved, each new SQLite grant, ordinary placement and direct reservation checks the pool's observed repository and registered resource size inside its budget transaction. The grant also has to match the registered provider leaf, execution fields and enrolled host binding. The transaction checks repository and pool runner counts independently of global, pool and host CPU, RAM, disk and runner budgets. A zero disk budget blocks a shared claim because it supplies no disk bound. These checks concern the cooperating ledger and do not establish a physical disk quota.

Every retained pool charge contributes to its observed repository, including unused grants, pending or uncertain reservations and inventory from a pool removed from policy. A missing or historically conflicting owner blocks growth. Each prospective award consumes repository headroom within the batch. An empty replacement policy closes growth. A ledger at revision zero retains its earlier capacity-only behavior and has no shared-repository policy to enforce. Schema 30 closes readiness on upgrade and preserves the outstanding charges. The version check fences existing v29 writers. Rollback requires stopping writers and retaining the current ledger for authoritative recovery.

Redemption checks the current caps with the existing grant counted once. It also requires the grant to have been issued after the most recent completed reconciliation, policy replacement and current enrolled profile revision. A newer barrier or revision therefore blocks old unused grants from being consumed. After validating the source, the grant cycle processes at most 64 unused grants in total across expiry and supersession. Before the TTL elapses, revocation rechecks the issuing audit entry, the superseding fence and the unused state under the SQLite writer lock. Only a committed expiry or revocation frees that grant’s headroom. Remaining candidates stay charged for later cycles. The same cycle rereads charges, revalidates the source and replans before it can issue a replacement. Consumed grants continue to charge their reservations. Reopening the store preserves these records and exact retries retrieve the existing result. [Shared policy checks](../../internal/admission/shared_policy_linux.go) · [Grant transaction](../../internal/admission/broker_grants_linux.go) · [Cross-pool contention, scope, disk and restart tests](../../internal/brokerinput/shared_admission_linux_test.go)

The offline grant cycle uses the existing demand priorities, repository weights and idle floors. Each new cycle grant ends at the earliest of its configured TTL, the demand request freshness deadline and the oldest required host observation's deadline. Each batch records when the evidence was evaluated. Issuance refuses a clock earlier than that bound. Issuance and redemption recheck the clock and host freshness inside the budget transaction before committing. Clock rollback before the recorded issuance makes an unused grant ineligible. Its charge remains until durable retirement. An unused legacy grant without the batch evidence bound remains charged and replayable. Enrolled policy excludes it from demand coverage and redemption. The installed-ledger guard reads persisted lineage even through generic database handles. Direct cycles reject installed ledgers before contacting the demand source, and new stock grant issuance, placement and retirement check the same guard under the writer lock. Historical batch or placement retries preserve the original commitment. A build that predates the new batch evidence field can reject batches with that field during canonical validation. Preserve the current ledger and keep writes closed pending compatibility checks during rollback. ## Missing guarantees for activation

The controller's stock receiver checks the verified client leaf and exact controller, provider and pool scope. Its create path resolves the profile and redeems an exact, already charged grant in the placement transaction. An installed deployment would still have to prove that **every** ordinary create for the proposed budget reaches this same authority before any native effect. Other GARM routes, controllers, scale sets and independent writers sharing the resource domain must be enrolled under the same limit or independently isolated. Active-runtime stock handlers and the grant loop continue to refuse activation. [Scoped receiver](../../internal/gatewayrpc/stock.go) · [Native stock bridge](../native-stock-bridge.md) · [Grant-loop guard](../../internal/brokerinput/service_linux.go)

Incus v6.0.4 project limits provide an additional project-level check. The create handler runs `AllowInstanceCreation` in a database transaction, then selects the create operation. The check evaluates the project with the requested instance included. Its aggregate CPU parser accepts integer, unpinned CPU counts and its memory parser requires absolute sizes. These paths alone establish neither a shared durable pre-effect reservation across projects nor settlement of delayed operations. An installed whole-host claim also requires the actual common physical parent, bounded competing consumers, and exclusive or independently fenced native create, start, restore and migration paths across restart. [Incus create check](https://github.com/lxc/incus/blob/a99413afd0c742da3bba10eb4f75d639f9dbbd32/cmd/incusd/instances_post.go#L1149-L1161) · [Create operation selection](https://github.com/lxc/incus/blob/a99413afd0c742da3bba10eb4f75d639f9dbbd32/cmd/incusd/instances_post.go#L1233-L1246) · [Project accounting](https://github.com/lxc/incus/blob/a99413afd0c742da3bba10eb4f75d639f9dbbd32/internal/server/project/permissions.go#L53-L108) · [Limit units](https://github.com/lxc/incus/blob/a99413afd0c742da3bba10eb4f75d639f9dbbd32/internal/server/project/permissions.go#L1489-L1514) · [Native proof requirements](../native-capacity-and-writer-boundary.md)

Keep the scope observe-only on provider, profile or host drift, incomplete inventory, unresolved settings changes, or lost writer authority. Rollback preserves the ledger and its outstanding charges. Reuse requires authoritative retirement evidence. A future activation additionally needs qualified operator stop and recovery, the independent release boundary, and explicitly authorized installed-stack evidence.
