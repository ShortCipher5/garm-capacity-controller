# Production shared capacity for stock GARM repository pools

**Draft engineering handoff.** This PR adds a plan, not enforcement. Source baseline: [main at fb8c39c](https://github.com/ShortCipher5/garm-capacity-controller/commit/fb8c39c26b865cc277783d8899af32dd63e6a836). Track the feature under [#53](https://github.com/ShortCipher5/garm-capacity-controller/issues/53). Rebase onto the latest main and recheck the cited contracts before coding.

## Goal and release boundary

Let several ordinary stock GARM repository pools share the finite capacity of one or more explicitly enrolled host scopes. The controller chooses bounded per-pool capacity targets from demand and reviewed policy; GitHub assigns jobs and stock GARM starts and retires runners through its normal provider. No GARM fork, queue proxy, independent runner lifecycle, or mandatory ZFS. No per-job live telemetry is required for the basic cap; the **Live per-job resource monitoring** plan may proceed in parallel, and its output is not proof of available capacity.

A ceiling is a concurrent admission invariant, not the sum of the most recently seen configured maxima. Example: of a six-slot shared budget, five charged slots (including unresolved work) leave one slot. If three repos want it, at most one additional slot can be committed across all reconciliations; it can go to none if the actual eligible host lacks the runner's full CPU or RAM footprint. A requested reduction from one pool never funds an increase in another. Define and separately track scopes not controlled by this deployment; never describe a subset budget as a whole-host hard limit unless all other consumers are bounded or isolated by independent verified controls.

## Agreed policy

- Default equal weight across repos (1), persist operator-selected positive weights by verified repository identity, and use deterministic tie breaking at equivalent demand and resource fit. Weight influences a choice between safe candidates, never the cap. Keep repo ceilings, pool ceilings, warm-idle floor and physical host budgets separate. A quiet repo may default to zero idle; configured positive idle floors are real demand for safe headroom, not guaranteed capacity when a budget is exhausted.
- Treat runner count, CPU and RAM as separate constraints at the host and applicable aggregate/repo/pool edges. Use explicit units (integer slots, millicpu, bytes), check arithmetic and canonical sizes, and evaluate unrouted or mixed runner classes independently. Support light/medium/heavy and custom profiles without treating labels as resource facts. Resolve host, authenticated provider/project and effective profile revision for the exact pool. An eligible-host list or reported configured capacity is not evidence of placement.
- Preserve disk reserves/pressure warnings as independent measured vetoes when applicable; never assume whole-host free storage is an enforceable per-runner quota or evidence of reclaimed storage. Use existing snapshot validity bounds and do not borrow a newer timestamp: a candidate expires at the earliest relevant policy, source, route, profile, capacity or pressure evidence deadline.
- Charge idle/busy runners, in-flight creates, outstanding commitments, retired-but-unproven remnants and unknown outcomes unless the current ledger already accounts for the same proven allocation. Deduplicate only with exact identities; conflicting evidence stays charged and can block growth. Unknown physical data cannot be converted to a zero. Observations can veto a decision, but neither counters nor a lower desired maximum prove release.

## Build sequence

1. **Normalize and validate inputs offline.** Assemble one coherent candidate from scoped demand, revisioned policy, relevant ledger charges, observed maxima/floors, authenticated source and eligible route, actual effective profile and independently scoped host evidence. Keep `PlanRoutedAllocatorProposal` pure and build on `BuildForStockScaling` where relevant; do not replace the current observe-only loop. Reject mixed scope, wrong provenance and incomparable or stale samples. Model absence, explicit zero, busy/unknown, and transient source failure as distinct states. Supply fixture cases and operator-visible bounded reason codes without credentials, raw job content, endpoints or reusable host secrets.
2. **Verify bounded reconciliation offline.** Use the existing stable-pair/batch semantics to generate a deterministic change candidate. Apply resource cost before selecting the next proposal. Test concurrency, different writers/revisions, stale evidence and restart via an isolated model using existing accounting invariants. On an already exhausted or externally drifted budget, refuse new admissions and show the overage; do not promise instant contraction or evict a busy runner. On restart, do not infer that a blank recent proposal history means no commitments remain. This slice may ship only as tests, diagnostics or observe-only planning while activation is unavailable.
3. **Qualify the actual boundary before live wiring.** Document evidence from a separately authorized isolated setup that a supported, exclusive, independently atomic admission mechanism covers all relevant stock create paths for the exact provider/project/host/profile, including concurrent creation and cases where activity may already be in flight. Obtain a supported stock settings mechanism with independently qualified outcome evidence from **Operator stop and recovery**, and authoritative credit only from **Safe runner-slot reuse**. Do not use read-then-write, transient GET readback, a shorter poll, scope widening, or a conflicting configuration to stand in for any missing guarantee. Do not build an alternative integration for any restricted path. If the proven mechanism is missing, keep writer flags off and record the concrete unsupported capability; do not proceed by enabling a test adapter.
4. **Only after qualification, wire and release incrementally.** Use the reviewed reconciliation route for the exact eligible scope; wire operator pause and unresolved changes to fail-closed growth. Require explicit activation, independent review and exact integrated CI. Enable a bounded change rate, preserve early observation and last known safe policy, independently observe effective limits and actual provider use, and pause or return to observe-only on drift. Rollback must retain unresolved charges and the stop/recovery barrier; no automatic retry, replacement, deletion, permissions change or capacity refund on ambiguity. Deployment, credentials and host conditions are separate approved operational steps, not part of this design PR.

## Dependency contracts

- **Operator stop and recovery → shared capacity:** only a separately qualified and current write-ready state allows planning to progress toward execution. During stop, unsupported, or unresolved outcome, never allocate from the uncertain capacity or infer that the prior update failed; read-only explanations remain safe. A restarted listener is not a completion receipt.
- **Safe runner-slot reuse → shared capacity:** consume the existing accounted resource view, including held and unknown charges; only the independently verified release path can create new headroom. Do not call a direct deletion or release routine from the allocator, and never use an idle observation, inactivity or a lowered setting to free a slot.
- **Shared capacity → operations:** a first isolated Mumbai observation can establish source/route/profile and ordinary job/runner facts only. The currently scoped one-job smoke cannot qualify a two-repo concurrency guarantee, ambiguous write recovery, or proof of teardown. Any expanded concurrency/failure trial needs its own isolated scope and approval; never use the live fleet to fill an evidence gap.

## Verification and definition of done

| Case | Required outcome |
| --- | --- |
| Three repos, one remaining slot; overlapping cycles or restart | At most one distinct commitment, including existing outstanding/deferred charges. No double spend or implicit refund. Run race and reopen checks with exact resource totals. |
| Equal and weighted demand; varying profile sizes | Stable decisions for shuffled input order, no duplicate demand per candidate pool, more opportunity for higher configured weight when capacity fits, and no cap override. |
| Route/profile revised, scope wrong, poll incomplete, stale pressure or exhausted headroom | No new growth on the affected scope; visible blocker, no misleading previous recommendation reused. Include arithmetic bounds, measured zero versus missing, and exact-boundary fit/no fit. |
| Scale-down with busy runner or unknown cleanup | No active disturbance; unsettled charge retained across reconciliation and restart. Proposed decreases create no new award credit. |
| Unknown settings result, stopped operator, v0.2.1, or fake claimed capability | Observe-only or blocked; no automatic retry, positive activation, or settings action. Preserve existing refusals even with plausible fixture inputs. |
| Real qualified stock setup | Separately record version/artifact, exact scope, approved isolated tests, independently verified CPU/RAM/slot results, cleanup, and rollback evidence. Confirm stock lifecycle unchanged. Record “unqualified” if any gate is unproven rather than counting fixture success. |
