# Separately approved native asset staging

The existing Add Server disclosure contains a dedicated asset-staging review. It uses only deployment-approved target IDs and fixed file metadata from the real asset service; no browser paths, keys, commands or arbitrary host destinations are accepted.

Review the preparation binding, permanent asset ID, SSH host/admin key pins, each file's bytes and hash, manifest digest and fixed upload script digest. Re-enter the separate asset token and explicitly approve the exact transfer. Acceptance means durable unknown status, not successful staging. The same ID cannot be uploaded again; reload actual status and approve inspection separately. Missing preparation bindings provide no usable plan.

Historical prepared receipts remain distinct from the latest attempt. Neither a historical receipt nor a successful inspection implies activation, installed OS packages, configured owner services, physical capacity or running jobs. Closing a view clears credentials/review and fences late responses but cannot undo an accepted remote action.

The review explicitly warns that temporary upload plus final staged files can approach twice the listed byte count, outside capsule quotas. This is a disk-cost warning, not a free-space or capacity qualification.
