# Native preparation in Servers

The existing server setup disclosure includes a separate native preparation action only after an authenticated load of deployment-configured targets. It uses its own token and target registry, not inventory-only credentials. Review the SSH administrator destination, pinned host key, administrator key fingerprint, immutable preparation ID, manifest/script digests and bundle size before approving transfer of the private owner configuration and TLS material.

The asynchronous POST is accepted only after durable unknown is recorded. Closing the browser does not roll back or stop the approved transfer. The UI clears its token and review, never automatically replays uploads, and requires a new authenticated status read. Unknown or historically prepared IDs offer explicit inspection only. An inspection does not re-upload or adopt partial files. An accepted inspection may fail while an older preparation receipt remains visible; that receipt does not prove the new inspection succeeded. All receipts are historical; prepared does not mean active, healthy, enrolled, qualified or running runners. No activation, reset or retry-upload control is provided.

This frontend depends on the actual native-preparation handler/service and protected deployment configuration. Disabled or invalid responses remove executable review rather than fabricate setup success. Unit and hosted browser regressions cover fixed request correlation, activation refusal, unknown-to-inspection behavior and interrupted response fencing. Local browser execution is not claimed.
