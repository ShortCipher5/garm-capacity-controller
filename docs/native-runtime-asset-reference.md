# Approved runtime asset references in owner assembly

The optional deployment-owned `nativebundle.Configuration.runtime_assets` field links an owner bundle to an exact approved runtime-asset manifest. It contains `manifest` (the existing `native-runtime-assets/v1` manifest) and `manifest_digest` (its canonical SHA-256). Static assembly recipes and registration catalog template build configurations both accept the same field. Browser requests cannot supply it.

The compiler validates the manifest, exact digest and target architecture, owns a copy of its entries, and derives only source paths beneath `/var/lib/garm-capacity/native-runtime-assets/<manifest.id>/`. It binds `runtime.raw`, `systemd-nspawn`, `zfs`, `zpool`, `ip` and `nft` to the appropriate artifact, launch, storage/quota and network-tool source fields and hashes. An existing nonempty path or hash must already equal that exact derived value; mismatches fail before bundle output creation. Leave these source fields empty to derive them. Packaged helper/TLS paths continue to be independently derived from the approved executable export and preparation ID.

Live owner-created image, registry, storage and network incarnation paths remain blank. Storage GUIDs, dataset names, quota budgets, network policy, selected CPU/RAM/partition limits and execution policy are not inferred or changed. The normal owner activation refusal remains in place.

Actual bundle results and assembly reports expose paired `runtime_asset_id` and `runtime_asset_manifest_digest`. These fields participate in immutable assembly digests and historical inspection compares them with the frozen recipe and actual reopened bundle/plan. Changing or removing the reference changes the reviewed recipe, not an existing completed assembly. Absent references preserve existing explicitly configured templates and historical digests.

This is configuration linkage only. Compilation does not read the host staging directory, upload or execute files, accept a staging receipt as current integrity, install libraries/packages, or establish boot, confinement, capacity or release authority. The manifest must describe a separately approved one-use per-target asset slot; this compiler does not derive new IDs or fabricate a source bundle. Existing asset transfer approval and permanent unknown/no-replay semantics are unchanged. Dynamic assignment of an asset recipe remains a separate reviewed integration.
